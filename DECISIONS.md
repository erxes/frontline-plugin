# Decisions

Where this port differs from the old erxes frontline plugin, and why. Each row
says what the old plugin did, what this one does, and the reason. A port adds
its rows in the same commit as the code. `MIGRATION.md` tracks what is ported,
and this file explains each place the port doesn't copy the old plugin.

## Whole plugin

| Old                                                                                     | New                                                                                                                                                                                                                                                            | Why                                                                                                                                |
| --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Mongo collections                                                                       | Postgres tables named `frontline_*`, each with `org_id` and forced row-level security                                                                                                                                                                          | Core and every plugin share one database on the new core                                                                           |
| Mongo `_id` strings                                                                     | Text ids that keep the old `_id`                                                                                                                                                                                                                               | An import can run twice and skip what it copied, and old links keep working                                                        |
| GraphQL resolvers, some with no permission check                                        | oRPC procedures on `reads` or `writes` with a permission and zod input                                                                                                                                                                                         | The access test walks every procedure and refuses a member without its permission                                                  |
| A separate `...TotalCount` query beside each list                                       | The count comes back with the list                                                                                                                                                                                                                             | One request per screen instead of two                                                                                              |
| Panel and filter state in Jotai atoms and `useSidePanel`                                | Records open in core's side panel (`?panel=`), filters live in `ListFilter`'s address                                                                                                                                                                          | A link or a reload opens the same record and filters, drawn by core                                                                |
| Unsaved edits kept by `usePanelFormDraft` on some panels                                | Core's panel keeps every draft until Save or Cancel                                                                                                                                                                                                            | Core owns drafts for every plugin                                                                                                  |
| Old users and customers were Mongo documents                                            | Waits on core's org import keeping their ids (erxes/erxes#10576)                                                                                                                                                                                               | The plugin's rows point at users and customers by old id                                                                           |
| Mail sync, token refresh, SLA checks and send retries ran in the plugin                 | Core's plugin jobs: the manifest's `jobs`, queued in the change's transaction, each module ports its own                                                                                                                                                       | Core retries and schedules them, so the plugin runs no queue (erxes/erxes#10577)                                                   |
| No filter bar                                                                           | `api/src/modules/filter.ts` compiles `ListFilter` rules until core exports its compiler (erxes/erxes#10574)                                                                                                                                                    | Core's compiler isn't open to plugins                                                                                              |
| Relative imports anywhere                                                               | `@/` and `~/` aliases; the lint rule waits on a release of @erxes/lint that has it (erxes/erxes#10573)                                                                                                                                                         | 0.1.3 shipped without core's rule                                                                                                  |
| Bulk delete sent one request per row, so one refusal left the rest deleted              | One transaction deletes every id or none                                                                                                                                                                                                                       | A half-done delete was the worst outcome                                                                                           |
| Client portal procedures (`cp*`), brands and segments                                   | Dropped                                                                                                                                                                                                                                                        | The new core has none of them                                                                                                      |
| The import ran tables in a fixed order, and one refused row aborted it                  | `scripts/import-mongo.ts` imports parents first, and skips and lists refused rows                                                                                                                                                                              | Children failed their foreign keys                                                                                                 |
| Default roles `frontline:admin`, `frontline:user` and `frontline:viewer`                | `admin`, `user` and `viewer` in `manifest.permissionSets`; the viewer reads the knowledge base and help centers                                                                                                                                                | Members keep one role in core, and an owner adds a set to it; no grant reads conversations or tickets without answering them       |
| A favorite star on page breadcrumbs                                                     | Dropped                                                                                                                                                                                                                                                        | Core's web has no favorites for plugin pages                                                                                       |
| `FrontlineMain` and `FrontlineSettingsLayout` drew the app's menu and its settings menu | `ui/src/Layout.tsx`: core's `AppLayout` sidebar with Settings pinned at its foot, which opens a sidebar of the settings pages with Exit settings, as core's Contacts draws them. `ui.frontline.gzip` rises from 54350 to 57100; the page module measures 57019 | The page module rendered bare routes, so a member on one page couldn't reach the others. The sidebar's 17 icons load on every page |
| `ui-modules`' member chip laid out its own avatar and name                              | `MemberLine` (`ui/src/shared/MemberLine.tsx`) wraps erxes-ui's `MemberInline` outside table cells, until it owns its layout ([erxes/erxes#10598](https://github.com/erxes/erxes/issues/10598))                                                                 | `MemberInline` returns a fragment, so a panel row showed the name under the avatar in large text                                   |
| A welcome notification with onboarding videos                                           | Dropped                                                                                                                                                                                                                                                        | Core sends no plugin welcome                                                                                                       |

## Channels

| Old                                                                                 | New                                                                                                                                                                                                                          | Why                                                |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `memberIds` on the channel beside `channel_members`, and stored counts              | Only `frontline_channel_members`, counts computed                                                                                                                                                                            | The two copies drifted and the counts went stale   |
| Roles admin, lead and member                                                        | Admin and member, `lead` folds into admin                                                                                                                                                                                    | Lead could only add members, which admins do       |
| A channel could lose its last admin                                                 | `removeMembers` and `setRole` refuse it                                                                                                                                                                                      | Nobody could manage that channel again             |
| `getChannels` and `getMyChannels`                                                   | One `channels.list`: members see their own, `frontline.channel.manage` sees all                                                                                                                                              | They differed only by filter                       |
| Confirms and counts said "1 channels"                                               | Singular and plural copy                                                                                                                                                                                                     | Plain grammar                                      |
| A channel list with its own search box, and a form page per channel                 | Core's list bar, `frontline:channel` in core's side panel, edited in place                                                                                                                                                   | Same features on core's screens                    |
| `channels.get` returned the member list                                             | `channels.members`, its own list under the filter bar                                                                                                                                                                        | The panel needs only ids, the members page filters |
| Lists searched only by name                                                         | `ListFilter` rules on every field, applied in SQL by `api/src/modules/filter.ts`                                                                                                                                             | Core's filter bar, one compiler for every list     |
| A `scope` of team or personal, and `getPersonalChannel`                             | `owner_id` marks a personal inbox; `channels.personal` makes one per member on the first visit to `/frontline/personal-channel`, which opens it in the channel panel. Only its owner sees it and the team list leaves it out | One column says whose it is; the scope repeated it |
| `channelMembersChange` sent a notification from the resolver                        | Adding members publishes `frontline.channel.members_added` with `notify`, in the change's transaction, to everyone added but the one adding                                                                                  | Core's notifications ride on the event             |
| `channelMoveResources` moved a channel's forms, pipelines and templates in one call | Each pipeline and template moves on its own panel; forms come back with the forms module                                                                                                                                     | No screen of the new UI moves them in bulk         |
| Forms and surveys pages under each channel, `/frontline/:id/forms` and `/surveys`   | `/frontline/forms` and `/frontline/surveys`, filtered by their Channel field                                                                                                                                                 | One list per record, narrowed like any field       |

## Response templates

| Old                                                      | New                                                                                                                     | Why                                               |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| A `showResponseTemplates` permission                     | The template's channel decides: members read, admins change                                                             | A template belongs to a channel                   |
| A `files` field                                          | Dropped                                                                                                                 | No screen set it                                  |
| `/frontline/:id/response/:responseId` was its own route  | It opens in core's side panel and expands to `/frontline/settings/response-templates/:id`; the old link redirects there | Records open like core's                          |
| `removeChannel` deleted only the channel and its members | Deleting a channel deletes its templates                                                                                | The templates stayed with no screen to reach them |
| Search matched the stored content, markup included       | Search and the Content filter match the words a member reads                                                            | A search for "paragraph" matched every template   |
| A form with Update saved an edit                         | Each field saves in place in the panel, the channel too                                                                 | Records edit like core's                          |

## Knowledge base

| Old                                                                                           | New                                                                                                           | Why                                                                                                               |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Mutations skipped the permission check                                                        | Every procedure checks its own permission                                                                     | Any member could change the knowledge base                                                                        |
| A Redis job published scheduled articles                                                      | Every article read first publishes the ones that are due                                                      | A lost job left an article unpublished                                                                            |
| Removing a topic searched the wrong field, and removing a category matched `categoryId`       | Foreign keys cascade: a topic takes its categories and articles, a category its articles                      | Both left orphans                                                                                                 |
| Children of a deleted category                                                                | Move to the top level                                                                                         | A dangling parent id hid them                                                                                     |
| Lists loaded the first 100 rows with no paging                                                | Articles page by cursor, 50 at a time                                                                         | Rows past 100 never showed                                                                                        |
| `topicsTotalCount` ignored the filters                                                        | The count folds into the list                                                                                 | The total disagreed with the rows                                                                                 |
| Category counts and authors ran one query per row                                             | One query for the page                                                                                        | N+1 queries                                                                                                       |
| `numOfArticles` counted only draft and published, and a parent didn't count its subtree       | Counts cover every status and the subtree                                                                     | The numbers were wrong                                                                                            |
| `publishedAt` was set only on draft to publish                                                | Set on every move to published                                                                                | Other paths left it empty                                                                                         |
| Edits fetched the detail and resent every field                                               | Updates are partial                                                                                           | Two editors overwrote each other's fields                                                                         |
| Bulk edits sent one request per article                                                       | `articles.bulkUpdate` is one statement                                                                        | Partial bulk edits                                                                                                |
| The parent rule refused only a direct loop                                                    | A full cycle check under a topic lock                                                                         | A category could become its own ancestor                                                                          |
| `code` unique across every organisation                                                       | Unique per organisation                                                                                       | One organisation's code blocked another's                                                                         |
| `topicId` on articles, `categoryIds` and `articleIds` on topics                               | Dropped, the category gives the topic                                                                         | Copies that drifted                                                                                               |
| `code` on articles, `forms`, `reactionCounts`, `publishedUserId`, `modifiedBy`, `createdDate` | Dropped                                                                                                       | No screen read them                                                                                               |
| `knowledgeBaseCategoriesGetLast`                                                              | Dropped                                                                                                       | No screen called it, and it ignored the topic                                                                     |
| Title and summary edited in their table cells                                                 | Every field is edited in place in core's side panel; status and category also in the row                      | Long text fits the panel, and records open as core's do                                                           |
| A sidebar of topics and their category trees, its width kept in storage                       | A topics list, the tree on the categories page, and a category rule in the filter bar                         | Core's lists narrow by the filter bar, not a sidebar                                                              |
| The knowledge base opened the first topic's articles                                          | It lists the topics, and a topic opens on its own page                                                        | A topic is a record with fields and counts of its own                                                             |
| An article was written in one form, body included                                             | Created from title, category, summary and status; the body is its Content tab                                 | Core drafts a record in its panel, and the long body needs its tab                                                |
| Articles listed in one table                                                                  | A list grouped by status, or the table, picked in the display menu                                            | Core groups a record with a status by it                                                                          |
| A status tab and a `categoryId` link narrowed the articles                                    | Filter bar rules on status, category, author, dates, views and privacy                                        | One filter for every field, kept in the link                                                                      |
| Topic settings edited the title, description and code                                         | Those are edited in the panel; settings hold language, colour and background                                  | Each field has one place to edit it                                                                               |
| Topics deleted one at a time                                                                  | Topics delete in bulk from the list's selection bar                                                           | Every other list deletes in bulk                                                                                  |
| The embed script, view counts and the public article page                                     | GET `/api/public/help-centers/:address` and its articles, which count each view; the embed script still waits | The address is a key frontline issued or a connected host, which `frontline_public_keys` maps to its organisation |
| Brand on a topic                                                                              | Dropped                                                                                                       | The new core has no brands                                                                                        |

## Pipelines and statuses

| Old                                                                                      | New                                                                                                                                                        | Why                                                                                                                                                  |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reads checked no access, and `ticketStatusesManage` ignored the channel                  | A pipeline and its statuses follow their channel: members read, admins change                                                                              | Any holder of the grant could edit every channel's statuses                                                                                          |
| A pipeline and its default statuses were written separately                              | One transaction                                                                                                                                            | A failure left a pipeline with no statuses                                                                                                           |
| `removePipeline` left its statuses, and `removeChannel` left its pipelines               | Both cascade                                                                                                                                               | Orphans                                                                                                                                              |
| Two status adds at once could share an order                                             | The add takes the next place under the channel lock                                                                                                        | Duplicate orders                                                                                                                                     |
| Reorder sent one update per status                                                       | `statuses.reorder` is one statement that refuses a stale list                                                                                              | A failure left a mixed order                                                                                                                         |
| One status query per stage                                                               | One `pipelines.statuses.list`                                                                                                                              | Six requests became one                                                                                                                              |
| Deleting a status asked nothing                                                          | It confirms first                                                                                                                                          | A misclick deleted it                                                                                                                                |
| `numberSize` was free text                                                               | An integer from 1 to 8                                                                                                                                     | Ticket numbers need a width                                                                                                                          |
| An SLA could hold two rules for one priority                                             | Refused                                                                                                                                                    | Which rule applied was undefined                                                                                                                     |
| Pipeline tabs were side panel record paths                                               | A pipeline is `frontline:pipeline` in core's side panel: Detail, Ticket statuses and SLA are its tabs, and `/frontline/settings/pipelines/:id` is its page | It opens and expands like core's records                                                                                                             |
| General, status and SLA forms saved with a button, statuses in a side form               | Every field, status and SLA time is edited in place and saves on Enter                                                                                     | Core's record panels edit in place                                                                                                                   |
| An SLA edit saved the policy as last fetched                                             | An edit shows in the panel at once, so the next one builds on it                                                                                           | Two quick edits lost the first; the pipelines spec finds core's number editor as the open popover's only box until it has a name (erxes/erxes#10607) |
| Pipelines and statuses were deleted one at a time                                        | The list and each stage pick several, and the selection bar deletes them in one transaction                                                                | All or none, as channels do                                                                                                                          |
| The pipelines list had no search or filter                                               | Core's filter bar: search, name, description, creator, created and updated dates                                                                           | The same bar as core's lists                                                                                                                         |
| `order`, `state`, `isHideName`, `tagId` on pipelines; `state`, `probability` on statuses | Dropped                                                                                                                                                    | No screen set them                                                                                                                                   |
| An attribution toast on the name field                                                   | Dropped                                                                                                                                                    | The field trims what it saves                                                                                                                        |
| The API fetched the pipeline creator with `users.findOne`                                | The UI names them with `MemberInline`                                                                                                                      | The API needs no `users:read` scope for it                                                                                                           |
| Deleting a pipeline checked for tickets; deleting a status checked nothing               | Both refuse while tickets use them                                                                                                                         | A status delete left tickets with no status                                                                                                          |
| A job rechecked SLA due times, a status could start an automation                        | The `tickets.sla` job warns and then breaches each clock; ticket events start core automations, and the status page has no seeded automation yet           | Core runs plugin jobs; seeding an automation from a plugin page is not in the contract                                                               |

## Tickets

| Old                                                                                                                                   | New                                                                                                                                                                                                                           | Why                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Numbers came from a `lastNum` shared by every pipeline with the same format, read and written outside a transaction                   | Each pipeline counts its own numbers while it is locked, and a number is unique in its pipeline                                                                                                                               | Two tickets made at once got the same number                                                 |
| A pipeline without a number size numbered tickets with a timestamp                                                                    | The number stays empty                                                                                                                                                                                                        | A timestamp reads as a number but isn't one                                                  |
| Number prefixes used the server's local date                                                                                          | UTC                                                                                                                                                                                                                           | The number doesn't depend on where the API runs                                              |
| The SLA was written by a second call after the save                                                                                   | Due times are set from the pipeline's rules in the ticket's transaction; the first response is stamped when a ticket first leaves a new status, the resolution when it reaches resolved or closed                             | A failure left a ticket without its SLA                                                      |
| SLA state was worked out in the browser and couldn't be filtered                                                                      | `tickets.list` returns each clock's state (due, overdue, met, missed), and the filter bar narrows by it                                                                                                                       | One answer for every screen, and a lead can list what is overdue                             |
| Any holder of `removeTicket` deleted any ticket                                                                                       | Members of the channel archive; its admins delete                                                                                                                                                                             | A delete can't be undone, an archive can                                                     |
| `updateTicket` and the bulk changes ran one write per ticket                                                                          | `tickets.bulkUpdate` and `tickets.bulkRemove` change every id or none, in one transaction                                                                                                                                     | One refusal left half the selection changed                                                  |
| A status change and a field change were separate mutations                                                                            | `tickets.update` takes any field, including another status of the ticket's pipeline                                                                                                                                           | One procedure per record, as core's records have                                             |
| Deleting a status or pipeline left its tickets behind, and deleting a channel left its tickets                                        | A status or pipeline in use refuses; a channel takes its tickets with it                                                                                                                                                      | Orphaned tickets showed in no list                                                           |
| Moving a ticket to a pipeline in another channel kept the old `channelId`                                                             | The ticket takes the pipeline's channel, and moving a pipeline moves its tickets                                                                                                                                              | Members of the new channel couldn't see them                                                 |
| Filters were one URL key each (`channel`, `pipeline`, `statusId`, `assignee`, `priority`, `state`)                                    | Core's filter bar, its rules in the address, on those fields plus number, SLA states, creator and five dates                                                                                                                  | The same filter as core's lists, on every field a ticket has                                 |
| Sort, direction and view were saved per browser under `ticketSort`, `ticketSortDirection` and `ticketView`                            | Sort and direction live in the address; the display is core's `DisplayMenu`, remembered per browser                                                                                                                           | A link opens the same order, and every list picks its display the same way                   |
| A table (`list`) and a board (`grid`) built for tickets, and a create sheet opened with C                                             | Core's `RecordList` grouped by status, a board by status and core's `RecordTable`; a ticket opens and is drafted in core's side panel                                                                                         | Tickets look and work like core's records                                                    |
| The board showed one pipeline at a time                                                                                               | It shows a column per status of every pipeline in view, and a card drops only on its own pipeline's statuses                                                                                                                  | The filter, not a separate pipeline pick, decides what shows                                 |
| `assignedMembers`, `subscribedUserIds`, tags, properties, branch, department, customers and companies on a ticket                     | Each is a ticket field: members, followers, plugin tags, properties, a branch and department from `frontline_teams`, and customers and companies by core id, also shown as a Tickets tab on core's customer and company pages | Core's tags and teams don't cover plugin records; the relation tab comes from `relationTabs` |
| Segments, export and import on the tickets page                                                                                       | Segments are dropped; export and import wait for core (erxes/erxes#10582)                                                                                                                                                     | The new core has no segments, and its import and export cover only its own records           |
| A status could refuse a move with a permission toast                                                                                  | The pipeline panel's Permissions tab names who may edit and move tickets in each status; the status select is disabled where they may not move it, and the API refuses                                                        | The rule lives there                                                                         |
| The list updated live over a GraphQL subscription with the changed ticket                                                             | Each ticket change calls `core_live_signal()` in its transaction, and open lists and panels refetch                                                                                                                           | Core's one stream carries signals, not data, and a signal sends only on commit               |
| No accessibility checks                                                                                                               | The tickets spec runs axe on each screen, a filtered list too                                                                                                                                                                 | Members reach every one of them                                                              |
| A detail page with its own layout, and a sheet for the same fields                                                                    | The ticket's Detail tab in core's side panel edits each field in place; expand opens it at `/frontline/tickets/:id`                                                                                                           | One place to read and change a ticket, as core's records have                                |
| `frontline_ticket_activities` and `frontline_tickets_notes`, with the plugin's own activity list and note box                         | Each change publishes a created, fields changed, moved or assigned event with `core_publish_event()` in its transaction; core's Activity tab shows them and holds the notes                                                   | Core keeps every record's timeline, and an event commits with its change or not at all       |
| Activity was written before the update with no transaction, and a pipeline move deleted the ticket's status history                   | One event per changed ticket from a before and after snapshot in the change's transaction; a move keeps the history                                                                                                           | A refused change left an entry for a change that never happened                              |
| Only the channel's members read a ticket's activity                                                                                   | Core shows the Activity tab to any holder of `frontline.channel.view` who opens the ticket                                                                                                                                    | Core checks a timeline's permission, not the record's channel (erxes/erxes#10579)            |
| Old activities and notes                                                                                                              | Not imported yet                                                                                                                                                                                                              | Core takes no imported timeline entries yet (erxes/erxes#10579)                              |
| `ui.config.gzip` was capped at 1850 bytes                                                                                             | 2000; seven record types' icons and slots, and the ticket's timeline, measure 1965                                                                                                                                            | Web loads `./config` on every page, and the ticket record type has to be there               |
| `ui.config.gzip` was capped at 2000 bytes                                                                                             | 2500; the help center record type, the ticket's contacts, the pipeline's Permissions tab and the Tickets relation tab measure 2467                                                                                            | Each is a record type, tab or relation web must know before it loads the module              |
| `ui.frontline.gzip` was capped at 51000 bytes                                                                                         | 51500; the settings pages, help centers and the personal inbox route measure 51481                                                                                                                                            | The page module holds the routes; each page is lazy                                          |
| Each status kept `departmentIds`, and each pipeline `departmentIds` and `branchIds`                                                   | Dropped; `isCheckDepartment` and `isCheckBranch` compare the ticket's department or branch with the member's teams                                                                                                            | No screen set the lists, and the checks read the ticket's own team                           |
| A member saw a department's tickets through core's `findWithChild`, and `CHECK_TEAM_MEMBER_SHOWN` switched it on for the organisation | Members and supervisors of a team see its tickets and those of the teams under it, where the pipeline checks departments or branches                                                                                          | The pipeline already says whether to check; one switch is enough                             |
| A branch's working hours paused the SLA clock                                                                                         | The SLA counts clock time                                                                                                                                                                                                     | Teams carry no working hours yet                                                             |
| Tickets were deleted with only an activity entry                                                                                      | Each change and deletion also goes to core's audit log with `core_record_audit()`                                                                                                                                             | Core's audit log is where owners look                                                        |
| An automation action "Create ticket"                                                                                                  | Not offered                                                                                                                                                                                                                   | Action fields can't pick a plugin's pipelines (erxes/erxes#10584)                            |
| Ticket and conversation reports, charts and their export                                                                              | Not ported                                                                                                                                                                                                                    | Core has no dashboard widgets for plugins (erxes/erxes#10581)                                |

## Settings

| Old                                                                               | New                                                                                                                        | Why                                                                              |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Core's tags with a `frontline:ticket` type, nested                                | `frontline_tags`, typed ticket or conversation, with no nesting, at `/frontline/settings/tags`                             | Core's tags cover customers, companies and products only                         |
| Core's departments and branches                                                   | Core's units, edited at core's `/settings/structure`; `frontline_teams` is a read-only copy, synced from `core.unit.*`     | Ticket visibility joins teams in SQL, and plugins can't join core's tables       |
| Core's fields and field groups per pipeline, and ticket configs choosing a layout | `frontline_ticket_properties`, org-wide, each naming the pipelines it shows on, at `/frontline/settings/ticket-properties` | One list replaces three; core's fields cover only its own records                |
| Ticket tags and fields in core's `tags` and `fields` collections                  | Not imported; tickets keep their `tag_ids` and `properties_data`                                                           | Those collections mix every record type, and the import copies whole collections |
| Settings pages inside the plugin's own settings layout                            | `/frontline/settings/*` pages in core's list shape; holders of `frontline.settings.manage` change them, others read        | Core has no plugin entries in its settings sidebar (erxes/erxes#10583)           |

## Help center

| Old                                                                                                      | New                                                                                                                                                            | Why                                                                                    |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `frontline_help_center_configs` with `erxesAppToken`, `clientPortalId`, `brandId`, CMS and ticket fields | `frontline_help_centers`: title, language, topic, colours, header and footer, and a domain                                                                     | Client portal, brands and CMS are dropped, and the ticket tab needed the client portal |
| A help center found by its client portal or its subdomain                                                | `frontline_public_keys` maps a public key or a connected host to the help center and organisation, as it maps form embed keys; listed in `tools/no-org-id.sql` | A public request carries no organisation                                               |

## Forms

| Old                                                                                                                            | New                                                                                                                                                                                                                                                                            | Why                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `showForms`, `formsAdd` and five more permissions on every form                                                                | A channel's members read its forms and submissions and correct or delete submissions; its admins change, duplicate, archive and delete forms                                                                                                                                   | Forms follow their channel, like tickets and pipelines                                          |
| `leadData`, a nested document on the form                                                                                      | Columns on `frontline_forms`: appearance, load type, colour, callout, thank-you text, steps, views and contacts                                                                                                                                                                | The API returns flat rows, and the filter bar reads columns                                     |
| Email to the visitor and admins, a redirect URL, custom CSS, templates, `isRequireOnce`, `verifyEmail` and the display `rules` | Dropped                                                                                                                                                                                                                                                                        | No screen of the new UI set them, and mail waits for its port                                   |
| `validation` and `regexValidation` on a field, a regex run as JavaScript                                                       | `validator`: a preset (email, phone, date…) or a pattern run by RE2                                                                                                                                                                                                            | A member's pattern can't hang the API on a visitor's text                                       |
| `frontlineFormFieldConversionCheck` before a field changed                                                                     | Dropped                                                                                                                                                                                                                                                                        | An answer outlives its field, so a removed field's answers still show on the submission         |
| One submission document per answer, joined by `groupId`                                                                        | A `frontline_form_submissions` row with one `frontline_form_answers` row per field                                                                                                                                                                                             | A submission has one id to open, filter and delete; the import maps `groupId` to that id        |
| `widgetsSaveLead` trusted the visitor's `cachedCustomerId`                                                                     | It is ignored; the customer comes from the answers' email or phone, found or made in core outside the transaction                                                                                                                                                              | Anyone could send another customer's id                                                         |
